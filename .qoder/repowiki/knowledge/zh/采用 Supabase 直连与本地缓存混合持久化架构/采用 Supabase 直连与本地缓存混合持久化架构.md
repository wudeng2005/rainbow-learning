# 采用 Supabase 直连与本地缓存混合持久化架构

_来源：e860060 → cbee9d5 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
应用初期仅使用 localStorage，导致用户更换设备或清除缓存时数据丢失。需要引入云端持久化以支持跨设备同步，同时保持单用户（rainbow-001）场景下的低延迟体验和离线可用性。

## 决策驱动
- 跨设备数据一致性
- 离线可用性与秒级恢复
- 减少网络请求频率
- 单用户无认证场景下的架构简化

## 备选方案
- **纯云端实时同步** _（已否决）_ — 优点：数据绝对实时，无需处理本地冲突；缺点：强依赖网络，每次操作都有网络延迟，离线不可用
- **引入后端 Edge Function 代理** _（已否决）_ — 优点：隐藏数据库细节，便于未来扩展复杂逻辑；缺点：增加架构复杂度，对于当前简单的 CRUD 和单用户场景属于过度设计
- **Supabase 直连 + localStorage 缓存层（选中）** — 优点：离线可用，启动时从本地秒级恢复，后台异步同步；直连客户端简化了单用户场景的开发；缺点：需要处理本地与云端的最终一致性，需实现同步调度器

## 决策
采用“本地优先”的混合架构：Zustand Store 作为内存状态，localStorage 作为持久化缓存层，Supabase PostgreSQL 作为最终数据源。通过 `src/lib/db/syncManager.ts` 实现 Session 粒度的批量同步（学习完成或页面隐藏时触发），App 启动时优先加载本地数据并异步拉取云端数据进行 Hydrate。在 `users` 表中冗余 `gems_total` 字段以避免每次 SUM 计算。题目数据保留在前端 JSON 中，不入库。

## 影响
实现了跨设备的数据同步和离线可用性。引入了同步逻辑的复杂性，需处理网络失败时的静默重试和本地数据的幂等迁移（UPSERT）。由于暂不开启严格认证，RLS 策略暂时全放行，存在潜在的安全敞口，需在后续多用户场景中收紧。
