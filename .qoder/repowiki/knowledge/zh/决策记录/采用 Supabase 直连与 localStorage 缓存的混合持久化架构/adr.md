# 采用 Supabase 直连与 localStorage 缓存的混合持久化架构

_来源：cbee9d5 → 026352a 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
Rainbow 快乐学堂原有数据仅存储在 localStorage，导致换设备或清缓存时数据丢失。需要实现跨设备数据同步，同时保持单用户（rainbow-001）场景下的低延迟体验和离线可用性，且暂不引入复杂认证体系。

## 决策驱动
- 跨设备数据一致性
- 离线可用性与秒级恢复体验
- 单用户场景下的架构简化
- 减少数据库写入频率

## 备选方案
- **纯云端实时同步（每次操作直接写 DB）** _（已否决）_ — 优点：数据实时性最高；缺点：网络依赖强，答题过程延迟高，频繁小写入增加 DB 负载
- **引入后端 Edge Function 作为 API 网关** _（已否决）_ — 优点：隐藏 DB 连接信息，逻辑集中；缺点：单用户无复杂逻辑场景下增加运维复杂度与冷启动延迟
- **Supabase 直连 + localStorage 缓存层（选中方案）** — 优点：离线可用，本地读取零延迟，Session 粒度批量同步减少请求数，无后端服务维护成本；缺点：需处理本地与云端数据冲突（通过 UPSERT 和启动时覆盖解决），匿名访问安全性较低（通过 RLS 临时全放行妥协）

## 决策
采用前端直连 Supabase PostgreSQL 的方案，保留 localStorage 作为高性能缓存层。实施 Session 粒度批量同步策略（答题过程写本地，完成/页面隐藏时同步云端），并在 App 启动时从 DB 拉取最新数据覆盖本地以实现幂等迁移和跨设备一致。在 users 表中冗余 gems_total 字段以避免聚合查询。

## 影响
实现了跨设备数据恢复和离线可用性，显著降低了数据库写入压力。但需维护 SyncManager 同步逻辑，且在多用户扩展前需重新评估 RLS 安全策略。题目数据仍保留在前端 JSON 中，未纳入数据库管理。
