本仓库的错误处理采用「前端静默降级 + 后端 API 透传抛出 + 会话级批量同步」三层模式，整体风格偏向容错优先、用户体验优先。

## 1. 系统/方法概述
- 无统一错误类型体系：未定义自定义 Error 子类或错误码枚举，所有网络层错误直接向上抛出 Supabase 返回的 error 对象。
- UI 层不捕获业务异常：页面组件（LearnPage / MathLearnPage / ReviewPage）在记录错题时仅调用 store 方法，不做 try/catch，依赖上层同步器兜底。
- 音频 I/O 静默吞错：src/lib/sounds.ts 对 Web Audio API 和 <audio>.play() 全部用 try/catch 包裹并空实现 catch，确保音效失败不影响主流程。
- 异步数据同步集中式容错：SyncManager 是唯一的持久化入口，内部用 try/catch 捕获所有并发任务失败，仅 console.error 记录，不中断本地状态。

## 2. 关键文件与职责
- src/lib/db/*.ts（progressApi / gemApi / errorBankApi / userApi）：数据库访问层，统一 if (error) throw error 模式，将 Supabase 错误原样上抛。
- src/lib/db/syncManager.ts：会话级批量同步器，聚合 pending 变更，Promise.all 并行执行，catch 后重试。
- src/store/useErrorBankStore.ts：错题本 Zustand store，纯内存操作 + 向 syncManager 入队待同步项。
- src/lib/sounds.ts：音效模块，所有 I/O 路径静默吞错。
- src/pages/LearnPage.tsx / MathLearnPage.tsx / ReviewPage.tsx：答题页，仅调用 store.recordError / recordCorrect，不处理异常。

## 3. 架构与约定
- API 层契约：每个 *.ts 中的 supabase 调用都遵循同一模板——解构 { data, error }，若 error 非空则 throw error，由调用方决定如何处理。
- 同步边界：用户交互只更新本地 Zustand 状态（localStorage 持久化），真正的 DB 写入集中在 syncAfterSession()，通过 visibilitychange 事件触发；失败不会回滚本地状态，下次可见性恢复自动重试。
- 幂等 upsert：错题、进度、宝石均使用 onConflict 的 upsert 语义，避免重复写入导致错误。
- 错误传播链：Supabase → API 函数 throw → SyncManager catch → console.error → 本地状态不变 → 下次重试。

## 4. 开发者应遵守的规则
1. 新增 DB 接口：沿用 const { data, error } = await supabase...; if (error) throw error 模板，不要自行包装错误类型。
2. 不要在 UI 层 try/catch 业务逻辑：答题结果记录走 store，异常由 SyncManager 统一兜底。
3. I/O 副作用一律静默：音频、动画等非核心功能出错必须 try/catch 吞掉，不得影响主流程。
4. 批量同步只追加不删除：pending 队列只在成功同步后清空，失败保持原样以便重试。
5. 避免在同步中抛错给调用者：syncAfterSession 的 catch 块不应 rethrow，保证页面渲染不受影响。

当前方案适合儿童学习类轻应用：以可用性为第一优先级，容忍网络抖动与浏览器限制，但代价是缺乏结构化错误上报与可观测性。
